## 🎯 Contexte métier

> *(Rempli par @ProductOwner)*

Le squelette applicatif Flutter livré par l'initialisation de la factory doit reposer sur une
qualité statique **reproductible et vérifiable** avant toute première fonctionnalité métier
(EPIC_01). Sans un référentiel de formatage et d'analyse statique appliqué dès le Sprint 0, chaque
US ultérieure hériterait d'une dette silencieuse (formatage incohérent, avertissements ignorés,
règles de lint désactivées sans traçabilité) qui rendrait les audits `/audit-us` peu fiables.

Cette US ne produit **aucune valeur utilisateur final** ; elle produit une valeur *plateforme* :
un socle de qualité de code de confiance, identique en local et en CI, sur lequel toutes les US
métier pourront être certifiées. **Règle du "Pourquoi"** : la fonctionnalité est justifiée car
elle conditionne la fiabilité de tous les gates qualité en aval — sans elle, `Certifié Prod` ne
peut pas être digne de confiance.

**Valeur ajoutée** : sur le squelette, `dart format` (formatage) et `flutter analyze` (lint +
typage statique) passent **sans erreur** (0 issue), et **aucune règle de lint n'est désactivée
sans justification écrite** — le tout rejouable à l'identique en CI (job `app-quality`).

## 📝 User Story

> *(Rempli par @ProductOwner)*

**En tant que** membre de la squad de développement (Developer, CodeReviewer, QA),
**je veux** une qualité statique de référence formalisée et vérifiée sur le squelette (formatage
conforme, analyse statique à zéro issue, aucune règle de lint désactivée sans justification),
**afin de** garantir un socle de code propre, cohérent et reproductible en CI avant la première
US métier, et de rendre les audits qualité fiables dès le Sprint 0.

## ✅ Critères d'Acceptation détaillés

> *(Rempli par @ProductOwner — plus détaillé que le backlog)*

### AC-1 : Formatage conforme (`dart format`)
- **Nominal** : sur le squelette, le gate `format` (`dart format --output=none --set-exit-if-changed lib test`) retourne un code de sortie `0` — aucun fichier de `lib/` ni `test/` n'a besoin d'être reformaté.
- **Erreur** : si au moins un fichier n'est pas formaté selon la convention Dart, la commande retourne un code de sortie ≠ 0, liste le(s) fichier(s) concerné(s), et le gate `format` échoue (bloquant).
- **Limite** : le périmètre de vérification est strictement `lib` et `test` (défini par le gate) ; un fichier de code situé hors de ces répertoires n'est pas couvert par ce gate — à documenter si un tel fichier apparaît.

### AC-2 : Analyse statique sans erreur (`flutter analyze`)
- **Nominal** : le gate `analyze` (`flutter analyze`) retourne « No issues found! », soit 0 error, 0 warning et 0 info/lint, avec un code de sortie `0`.
- **Erreur** : toute issue remontée (error, warning ou lint) fait échouer `flutter analyze` (code de sortie ≠ 0) ; le gate `analyze` est bloquant et interdit la progression de l'US.
- **Limite** : l'analyse porte sur les plateformes réellement scaffoldées (Android, Web) ; iOS n'étant pas scaffoldé (limitation connue documentée dans `STACK_PROFILE.md`), il est hors périmètre d'analyse — ce n'est pas un contournement de règle et doit rester tracé comme une limitation, pas comme une exception silencieuse.

### AC-3 : Aucune règle de lint désactivée sans justification écrite
- **Nominal** : dans `analysis_options.yaml`, le set de base `package:flutter_lints/flutter.yaml` est inclus ; aucune règle n'est désactivée (`nom_regle: false`). Si une désactivation existe, elle est accompagnée sur la même zone d'un commentaire de justification explicite (le pourquoi métier ou technique).
- **Erreur** : une règle désactivée **sans** commentaire de justification est un défaut ; elle doit être détectée (revue @CodeReviewer / gate qualité) et corrigée — soit en réactivant la règle, soit en ajoutant la justification écrite.
- **Limite** : les lignes d'exemple commentées héritées du template (ex. `# avoid_print: false`) sont inertes et ne comptent pas comme désactivations effectives ; en revanche toute suppression locale dans le code (`// ignore: <regle>` ou `// ignore_for_file: <regle>`) compte comme une désactivation et exige la même justification écrite.

### AC-4 : Qualité statique reproductible en CI
- **Nominal** : la même séquence (format + analyze) s'exécute via `python scripts/run_gates.py` en local et dans le job CI `app-quality` (`ci.yml`), en s'appuyant exclusivement sur les commandes de `factory.config.json`, et produit le même résultat (vert) sur une PR de l'US.
- **Erreur** : toute divergence local vs CI (fichier non commité, version d'outil incohérente, règle contournée en local seulement) fait échouer le job `app-quality` sur la PR et bloque le merge.
- **Limite** : la commande stack n'est jamais codée en dur hors de `factory.config.json` (source unique) ; un ajustement de commande ou de périmètre passe par la config et sa synchro (`factory_sync.py --check`), jamais par un contournement local non tracé.

## 🏗️ Contexte technique

> *(Rempli par @Architect lors de la phase `technical_validation` — chemins et outillage selon `docs/governance/STACK_PROFILE.md`)*

> **Nature de l'US** : configuration/validation, sans code applicatif Dart nouveau. On **valide et
> formalise** la qualité statique de l'existant — on ne durcit PAS le lint-set (voir « ADR associé »).

### Fichiers concernés

| Fichier | Type | Ce qui doit changer |
|---|---|---|
| `analysis_options.yaml` | Config lint/analyse (racine) | **Validation, pas durcissement.** Confirmer `include: package:flutter_lints/flutter.yaml` et que `linter.rules` ne contient **aucune désactivation effective** (les 2 lignes d'exemple actuelles sont commentées, donc inertes). Ne rien ajouter de strict. Si une future désactivation apparaît, elle porte un commentaire de justification sur la même zone. |
| `pubspec.yaml` | Manifeste (dev-deps) | **Lecture seule.** Confirmer `flutter_lints: ^6.0.0` présent en `dev_dependencies`. Aucun ajout de lint-set dans cette US. |
| `lib/main.dart`, `test/widget_test.dart` | Code squelette (cibles des gates) | Ne pas modifier fonctionnellement. Reformater **uniquement** si `dart format` le réclame. Ce sont les seuls fichiers Dart existants. |
| `reports/US-00.2/` | Preuves exécutables (Constitution Art. 3) | À créer. Y déposer les sorties de `run_gates.py --gate format` et `--gate analyze` (preuve reproductible local ↔ CI). |

### Patterns imposés

- **Config lint unique** : `analysis_options.yaml` racine est l'unique source des règles de lint/analyse (Art. 4 « seuil qualité unique » appliqué au lint). Aucune règle dupliquée ni contredite ailleurs.
- **Justification obligatoire de toute désactivation** : toute `nom_regle: false` en config, ou toute directive `// ignore: <regle>` / `// ignore_for_file: <regle>` dans le code, exige un commentaire de justification adjacent (STACK_PROFILE §Developer + AC-3). **Ce contrôle est une revue @CodeReviewer, pas un gate automatisé** (voir Risques).
- **Commandes stack jamais en dur** : `format` et `analyze` s'exécutent exclusivement via `python scripts/run_gates.py`, sur les commandes définies dans `factory.config.json` (Art. 4). Interdit de recopier une commande Flutter/Dart ailleurs.
- **Non-durcissement (périmètre figé)** : on valide l'existant `flutter_lints`. Aucun lint-set additionnel (very_good_analysis, lints custom), aucun `--fatal-infos`, aucune règle strict ajoutée dans cette US.

### Contraintes architecturales

- **Commandes EXACTES (source unique `factory.config.json` → `adapter.components.app.gates`)** :
  - Gate `format` : `dart format --output=none --set-exit-if-changed lib test` — portée strictement `lib test`.
  - Gate `analyze` : `flutter analyze` — analyse **tout le package Dart** (pas seulement `lib`/`test`).
  - Orchestration : `python scripts/run_gates.py --gate format` / `--gate analyze` / `--component app`.
- **Reproductibilité CI (AC-4)** : le job `app-quality` (`.github/workflows/ci.yml`) rejoue `python scripts/run_gates.py --component app` sur Flutter **3.44.7** stable après `flutter pub get` → verdict identique local ↔ CI. Le poste dev doit être aligné sur cette version (STACK_PROFILE §Runtimes).
- **Périmètre plateformes** : Android + Web scaffoldés ; **iOS non scaffoldé** (limitation connue STACK_PROFILE) donc hors périmètre d'analyse — c'est une limitation tracée, **pas** un contournement de règle (AC-2 limite).
- **Fichiers d'enforcement intouchables (Art. 6)** : `factory.config.json`, `scripts/*`, `.github/*`, `.claude/hooks/*` ne sont pas modifiés par cette US. Tout ajustement de commande ou de périmètre passerait par la config + `python scripts/factory_sync.py --check` (jamais par un contournement local).

### Dépendances

| Type | US / Composant | Raison |
|---|---|---|
| **Dépend de** | Initialisation factory (squelette Flutter livré : `lib/main.dart`, `test/widget_test.dart`, `flutter_lints ^6.0.0`) | Les gates `format`/`analyze` exigent un squelette compilable et `flutter_lints` résolu (`flutter pub get`). **Aucune US préalable bloquante.** |
| **Bloque** | Toutes les US métier (EPIC_01, en premier **US-01.1**) | La fiabilité des audits `/audit-us` et de `Certifié Prod` repose sur cette qualité statique de référence (cf. Contexte métier). |

### Risques et points d'attention

- ⚠️ **AC-3 non couvert par un gate automatisé** : aucun script du référentiel (`format`/`analyze`/`test`/`deps_audit`/`build`) ne détecte une règle désactivée *sans justification*. `flutter analyze` ne peut par nature pas signaler une règle qu'on a désactivée. L'enforcement de l'AC-3 est donc une **revue manuelle @CodeReviewer**. Le « le gate qualité échoue » du Scénario Gherkin 4 doit se lire **« le contrôle de revue échoue »**, pas « un script sort en erreur ». À expliciter pour @QA_Tester et @CodeReviewer.
- ⚠️ **Durcir le lint casserait le squelette** : ajouter un lint-set strict (very_good_analysis) ou `--fatal-infos` ferait potentiellement échouer `flutter analyze` sur le code d'exemple → **hors périmètre** de cette US (décision structurante = US + ADR dédiés).
- ⚠️ **Faux sentiment de sécurité si périmètre trop étroit** : `dart format` ne couvre que `lib test`, alors que `flutter analyze` couvre tout le package. Un futur fichier Dart hors `lib`/`test` serait analysé mais **pas** contrôlé en formatage — à documenter dès qu'un tel fichier apparaît (AC-1 limite). Aujourd'hui sans objet (seuls `lib/main.dart` et `test/widget_test.dart` existent).
- ⚠️ **Sévérité de `flutter analyze`** : la commande figée `flutter analyze` échoue (exit ≠ 0) dès qu'une issue (info/warning/error) est remontée ; le squelette est actuellement à « No issues found! ». Ne pas ajouter `--fatal-infos` (= durcissement) dans cette US.
- ⚠️ **Divergence local ↔ CI** : version d'outil non alignée ou fichier non commité ⇒ AC-4 peut diverger. Mitigation : Flutter épinglé 3.44.7 en CI, exécution via `run_gates.py` uniquement.

### ADR associé

> Track **STANDARD** → ADR non obligatoire par défaut (`docs/governance/TRACKS.md`).

**Aucun ADR pour cette US** : elle **valide l'existant** (`flutter_lints` déjà inclus, 0 désactivation effective) — aucune décision d'architecture structurante n'est prise.

**ADR requis si durcissement** : si une US ultérieure décide d'un lint-set plus strict (very_good_analysis, règles custom, `--fatal-infos`, changement de portée des gates), cette décision est structurante et exige un **ADR dédié** (`docs/adr/ADR-XXX-*.md`) — et probablement un passage en track supérieur. Ce durcissement ne doit **pas** être mélangé à l'établissement de la référence.
