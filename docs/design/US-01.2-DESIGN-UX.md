## 2. Arborescence des écrans

```
Hub (racine, existant)
│   AppBar « Concentration »
│   Grille 1→9 tuiles  |  Placeholder d'état vide
│   Barre basse : [Échéances actif] [Respiration grisé] [Concentration grisé] [+ ACTIF] [⚙ inerte]
│                                                                              │
└── (activation de « Gérer les échéances ») ─────────────────────────────────►┘
    │
    └── Page de gestion  (route poussée, retour = hub)
        │   État VIDE            → message sobre + affordance d'ajout
        │   État NOMINAL         → groupe « Actives » puis groupe « Échues »
        │   État à 9 présentes   → affordance d'ajout marquée INDISPONIBLE (mais activable)
        │   ⛔ pas d'état « chargement » · ⛔ pas d'écran d'erreur technique  (§5)
        │
        ├── Formulaire  (route poussée : « Nouvelle échéance » | « Modifier l'échéance »)
        │       Annuler / retour système  ⇒ retour gestion, ⛔ AUCUNE écriture
        │       Enregistrer               ⇒ refus inline, OU retour gestion
        │
        └── Confirmation de suppression  (dialogue modal, au-dessus de la gestion)
                Annuler / Échap / hors-cadre ⇒ ⛔ AUCUNE écriture
                Supprimer                    ⇒ écriture, retour gestion
```

**Trois décisions de structure, avec leur motif** :

* **La page de gestion est une ROUTE, pas un onglet, et elle ne porte PAS la barre basse.**
  Motif : le scénario « Ouvrir la gestion ne rend pas interactifs les modules grisés » vérifie les
  modules **sur le hub**, après retour *(« la page de gestion a été ouverte puis refermée … je touche
  les modules … sur le hub »)* — la barre n'a donc rien à faire sur la page de gestion ; l'y
  dupliquer ferait **deux exemplaires d'un composant** et **rouvrirait le risque de débordement du
  `Row`**, déjà payé une fois *(63 px à 390 de large, 133 px à 320)*.
* **Le formulaire est une ROUTE PLEIN ÉCRAN, pas une modale centrée** *(la maquette Stitch en fait une
  modale)*. Motif mesurable : à **200 % d'échelle de texte** *(exigence WCAG 1.4.4, §7)*, une modale
  centrée de hauteur contrainte **rogne** ; sur un téléphone, clavier ouvert, il reste moins d'un
  tiers de la hauteur. La modale de la maquette est un patron **desktop** *(`max-w-md mx-auto`)*.
* **La confirmation de suppression EST une modale.** Motif : ce n'est pas une surface de saisie mais
  une **décision**, et c'est le **seul acte destructif du produit** — il faut **capturer le focus**
  pour qu'aucune autre commande ne soit atteignable pendant la question.

### 3.3 Page de gestion — 9 échéances présentes *(AC-5, clarify nº 3)*

```
│  ┌────────────────────────────────┐  │
│  │  +   Ajouter une échéance      │  │  bouton CONTOUR (bord 1 contour,
│  └────────────────────────────────┘  │  texte texteSecondaire) ⛔ PAS grisé
│  Limite de 9 échéances atteinte.     │  ← LE MESSAGE DU DOMAINE, mot pour mot
│  Supprimez une échéance existante    │     (§9.3) — texteSecondaire, 14
│  pour en créer une nouvelle.         │
```

🔴 **L'affordance reste ACTIVABLE.** ⛔ **Pas de `Semantics(enabled: false)`, pas de bouton
désactivé.** Deux raisons, toutes deux mesurables :
1. le `.feature` exige **« je tente de créer une dixième échéance valide »** — un bouton désactivé
   rend la **tentative inobservable**, donc le scénario **intestable** ;
2. l'arbitrage *clarify nº 3* dit littéralement **« indication, pas barrière »**, et *« un bouton
   simplement grisé ne dit ni POURQUOI ni COMMENT sortir »*.
➡️ **L'activer ouvre le formulaire**, qui porte le **même message** en tête, et la **validation à la
soumission refuse** — c'est **ce refus** qui est falsifiable *(le stockage contient toujours 9)*.
*(Lecture du mot « valide » du scénario : la donnée a été saisie, donc le refus intervient à la
soumission. Variante écartée : refuser dès l'activation, ce qui viderait le mot « valide » de son
objet. **Point soumis au @PO au §11.4** — il touche un comportement observable d'AC-5.)*

### 3.5 Confirmation de suppression *(AC-7 — seul acte destructif)*

```
        ┌────────────────────────────────┐
        │  Supprimer cette échéance ?    │  titre 20/w600, texteSurFond
        │                                │
        │  « Convention annuelle » sera  │  16, texteSurFond — NOMME la cible
        │  définitivement supprimée.     │
        │  Cette action est irréversible.│
        │                                │
        │        Annuler     Supprimer   │  Annuler = focus INITIAL
        └────────────────────────────────┘     Supprimer = token erreur + le MOT
```

* **Le focus initial est sur « Annuler »**, jamais sur l'action destructive.
* **Échap**, **retour système** et **appui hors du cadre** valent **Annuler** ⇒ ⛔ **aucune écriture**
  *(le critère C-7 du Story File exige que le fichier soit **inchangé entre la demande et la
  confirmation** — le design doit donc n'écrire **qu'après** le geste « Supprimer »)*.
* **La cible est nommée dans le corps du dialogue.** À 9 lignes qui se ressemblent, une confirmation
  anonyme *(« Supprimer ? »)* est une **confirmation sans information**.
  ⚠️ **Cas de l'échéance à description vide** *(invariant I-3, scénario « Une échéance à description
  vide reste listée et manipulable »)* : le corps dit alors **« L'échéance du 15 mars 2027 à 23:59
  sera définitivement supprimée. »** — ⛔ **jamais des guillemets vides**.
* **La distinction Annuler / Supprimer ne repose PAS sur la couleur** *(§6.4)* : elle repose sur le
  **mot** et sur l'ordre.

### 4.1 Carte d'échéance — anatomie et accessibilité

```
Semantics(container: true)
├─ Text  description   16/w500 texteSurFond   maxLines 1, ellipsis
├─ Text  « 15 mars 2027 · 23:59 »   14/w400 texteSecondaire
└─ Row
   ├─ Text  temps restant   14/w500 texteSecondaire      (Expanded)
   ├─ IconButton ✎   48×48   label « Modifier <description> »
   └─ IconButton 🗑   48×48   label « Supprimer <description> »
```

🔴 **Le libellé d'accessibilité d'une action NOMME l'échéance.** À 9 cartes, neuf boutons annoncés
*« Modifier »* sont **neuf boutons indistinguables** pour un lecteur d'écran. *(Pour une description
vide : « Modifier l'échéance du 15 mars 2027 ».)*

### 4.2 Le temps restant en gestion — ⚠️ **point signalé, pas contourné**

AC-8 « Limite » et le `.feature` exigent l'unité en gestion *(« son temps restant avec son unité,
soit **3 jours** »)*, et le Story File écrit que la ligne l'obtient **« en réutilisant
`RemainingTime.libelleAccessibilite` »**.

🔴 **Mesuré dans le code d'US-01.1** *(`remaining_time_calculator.dart`)* :
`libelleAccessibilite` vaut `'$nombre ${unite.libelle(nombre)}$suffixe'`, où
`suffixe = ', ${echeance.description}'`. **La chaîne EMBARQUE la description.** L'afficher verbatim
dans une carte qui porte déjà la description rendrait :

> Convention annuelle
> 15 mars 2027 · 23:59
> **3 semaines, Convention annuelle**

➡️ **Ma spécification** : la carte affiche **`nombreAffiche` + `unite.libelle(nombreAffiche)`**,
c'est-à-dire **exactement ce que le moteur a produit**, ⛔ **sans aucun calcul de durée dans la
présentation** *(risque **R-9** respecté à la lettre)* ; et le **`Semantics` de la carte** utilise,
lui, **`libelleAccessibilite` entier** — c'est précisément ce pour quoi il a été écrit.
Pour une **échue**, `libelleAccessibilite` vaut *« échéance atteinte, … »* ⇒ la carte affiche
**« Échéance atteinte »**.
⚠️ **Divergence assumée avec la LETTRE du Story File** *(« en réutilisant `libelleAccessibilite` »)*,
**signalée ici et au §10.1** — ⛔ elle ne modifie **aucun** AC ni aucune étape Gherkin, et la
contrainte réelle *(un seul moteur de calcul)* est **tenue**.

### 4.3 L'affordance « Modifier » sur une échue — ⚠️ **présente et activable**

Le scénario est : *« **Quand je tente de modifier cette échéance** / Alors la modification est refusée
par un message indiquant qu'une échéance échue **se consulte ou se supprime** »*.
⇒ **Retirer l'icône ✎ des cartes échues rendrait le scénario intestable.** Elle est donc **présente,
activable**, et son activation **n'ouvre pas le formulaire** : elle affiche le **message de refus**
*(même composant C-5, ancré sous la carte, `liveRegion`)*.

📌 **Règle unifiante du design d'US-01.2, née de ces deux cas** :
> ⛔ **Aucune barrière muette.** Toute règle qui refuse est **atteignable par un geste** et **rend un
> message**. Un contrôle rendu inatteignable n'est pas une protection — c'est une **clause devenue
> inobservable**.

### 6.4 Ce que la couleur n'a PAS le droit de porter seule

| Information | Porteur **obligatoire** | ⛔ Interdit |
|---|---|---|
| Un refus de validation | le **mot** *(« La description est obligatoire. »)* + un **signe** ⚠ | la seule teinte `erreur` |
| L'état **échue** d'une carte | les **mots « Échéance atteinte »** + le **liseré** de 2 dp | un simple assombrissement |
| L'affordance d'ajout **indisponible** | le **message de la limite**, affiché | un bouton simplement pâle |
| L'action **destructive** du dialogue | le **mot « Supprimer »** + sa **position** | la seule teinte `erreur` |

### 6.5 ⛔ Aucune opacité sur un token de texte — règle nouvelle, née d'une mesure

La maquette Stitch construit **toute** sa hiérarchie par l'alpha : `text-on-surface-variant/40`,
`/50`, `/60`, `/80`, et un `opacity-40` sur **la section entière** des échues *(« Historical
Context »)*.

🔴 **Appliqué au token retenu, `opacity-40` donne `#69574F`, soit `2,72:1`** — sous les 4,5:1 **et**
sous les 3:1. Et il frapperait **précisément le groupe des échues**, dont le @ProductOwner écrit
qu'il doit *« rendre les candidates à la suppression **évidentes**, puisque c'est la **seule** issue
quand la limite est atteinte »*. **Estomper de 40 % le seul groupe sur lequel il faut agir est
l'inverse du besoin.**

➡️ **Règle** : la hiérarchie se fait par **un token mesuré**, par la **taille** et par la **graisse**
— ⛔ **jamais par l'alpha**. *(Une opacité fabrique une couleur nouvelle, donc un contraste que
personne n'a calculé.)*
⚠️ **Hypothèse écrite** : Flutter compose `Opacity` en **sRGB (gamma)**, donc la couleur effective
est la moyenne pondérée des **composantes 8 bits**. En lumière **linéaire** le résultat serait plus
clair. L'hypothèse est **dans le script** *(fonction `composer`)*, donc **contestable et rejouable**.

### 9.3 Le texte des messages vit en **un seul exemplaire**

Le pattern nº 10 du Story File l'impose : *« le texte des messages d'erreur vit en UN seul

> retrouve une liste qui a l'air normale.

Cette règle unique couvre les **trois scénarios** d'AC-17 et évite d'en écrire une par cas. Elle est
la **jumelle** de la règle « aucune barrière muette » du §4.3 : l'une interdit de rendre un refus
inatteignable, l'autre interdit de rendre un échec invisible.

#### 14.2.1 Extension des composants — ⛔ **aucun composant nouveau**

| Composant | Statut | **Extension datée 2026-08-06** |
|---|---|---|
| **C-4** *(champ de saisie)* | **étendu** | l'état « en erreur » impose désormais que **la valeur saisie reste littérale** *(§14.1.1)* |
| **C-5** *(message de validation)* | **étendu** | **3ᵉ ancrage : le PIED DE L'ACTION** — immédiatement **au-dessus** du bouton qui a échoué, pour un message qui **ne vise aucun champ**. *(Les deux premiers restent : sous un champ · en tête de formulaire pour la limite de 9.)* |
| **C-7** *(dialogue de confirmation)* | **étendu** | **2ᵉ état : « échec »** — le dialogue **reste ouvert** et porte un **C-5** posé sur `surfaceElevee` |
| ⛔ **Rien d'autre** | — | ⛔ pas de bandeau, ⛔ pas de `SnackBar`, ⛔ pas d'écran d'erreur, ⛔ pas de bouton « Réessayer » |

**Règle d'ancrage de C-5, en un seul énoncé** *(elle rend les trois ancrages déductibles au lieu
d'être une liste à retenir)* :
> **Le message est ancré sur CE QUI A ÉCHOUÉ** : un **champ** si c'est un champ, l'**action** si
> c'est l'action.

⛔ **Pourquoi PAS de bouton « Réessayer »**, alors que le réflexe l'appellerait : le scénario dit
*« Quand le stockage local redevient inscriptible et **que je valide de nouveau** »* — **« Enregistrer »
EST le réessai**. Un second bouton serait une **deuxième affordance pour une même action**, donc deux
chemins qui dérivent *(même classe que R-10)*, et il faudrait décider ce qu'il fait de la validation.
⛔ **Et PAS de `SnackBar`** : le §5 l'interdit déjà pour un refus de validation *(« qui disparaît
avant d'être lu »)* ; ici le coût est pire — **un message manqué se lit comme un enregistrement
réussi**.

| Variante | Ce qu'elle coûte | Verdict |
|---|---|---|
| **(a) Le dialogue reste ouvert et porte le message** | 0 ancrage nouveau ; **une seule règle** pour le formulaire **et** le dialogue ; le réessai est à **un geste**, focus déjà en place | ✅ **RETENUE** |

#### 14.2.4 Trois interdits qui viennent des clauses, pas du goût

| Interdit | Clause qui l'impose | Ce qui le réfuterait |
|---|---|---|
| ⛔ **Aucune mise à jour optimiste.** L'interface **ne montre jamais** une échéance avant que l'écriture ait **réussi** ; elle **ne la retire jamais** avant que la suppression ait **réussi** | AC-17 « Erreur » : *« la création **n'apparaît pas** … une suppression échouée **laisse l'échéance en place** »* | La carte apparaît puis **disparaît** · la carte disparaît puis **revient** *(les deux sont des « flashs » que l'œil enregistre comme une perte de donnée)* |
| ⛔ **La garde « un seul vol » se RELÂCHE à l'échec.** Le §5 ignore une seconde activation **pendant** l'écriture ; à l'**issue** d'un échec, la commande **redevient activable** | AC-17 « Erreur » : *« la nouvelle tentative aboutit **sans ressaisie** »* | Après un échec, « Enregistrer » reste inerte ⇒ le 2ᵉ scénario d'AC-17 est **inobservable** |
| ⛔ **Aucune confirmation d'abandon** en quittant le formulaire *(« voulez-vous vraiment abandonner ? »)* | AC-17 « Limite » : *« quitter le formulaire abandonne la saisie, et **c'est la seule perte admise** »* ; et §3.5 : la confirmation de suppression est le **seul** dialogue du produit, pour le **seul** acte destructif | Un second dialogue modal apparaît · « Annuler » demande une confirmation |

⚠️ **Conséquence assumée et nommée du troisième interdit** : après un échec, « Annuler » est **à côté**
d'« Enregistrer » et sa conséquence est **plus lourde** qu'avant *(la saisie n'est nulle part)*.
**Je l'accepte** parce que la clause « Limite » d'AC-17 la prescrit **littéralement**, et parce que le
message d'échec est **déjà affiché** quand l'utilisateur décide : ⛔ **il n'abandonne pas dans
l'ignorance.**

#### 14.2.5 Les trois issues d'« Enregistrer » — extension du §2

```
Formulaire · « Enregistrer » a désormais TROIS issues, là où le §2 en dessinait deux :

  ① refus de VALIDATION  → C-5 SOUS LE CHAMP fautif        ⛔ aucune écriture TENTÉE
  ② échec d'ÉCRITURE     → C-5 AU PIED DE L'ACTION         ⛔ écriture tentée, ÉCHOUÉE
  ③ écriture réussie     → retour à la page de gestion

⛔ ① et ② NE COEXISTENT JAMAIS : on n'écrit que si la validation passe.
⇒ un formulaire qui afficherait les deux messages en même temps est un DÉFAUT.
```

⚠️ **Le §2 n'est pas repeint** — il dit *« Enregistrer ⇒ refus inline, OU retour gestion »*, ce qui
reste **vrai à sa date et à sa phase** *(AC-17 n'existait pas)*. **Ce bloc l'étend.**

#### 14.2.6 Le web — ⛔ **aucune surface spéciale**, et c'est délibéré

AC-17 « Limite » : sur le web, **toute** écriture échoue et **le même message** s'affiche.
➡️ **Conséquence de design, sous forme d'interdit** : ⛔ **la présentation ne détecte PAS la
plateforme.** Pas de `kIsWeb` dans un widget, pas de bandeau « non pris en charge », pas de message
différent. **Réfuté par** : une branche de plateforme dans le code de présentation, ou un texte
visible qui parle du web.
✅ **Aucune surface n'est à dessiner** : l'écran web est la **composition de deux règles déjà
écrites** — au démarrage, si rien n'est lisible, c'est l'**état vide sobre** *(§3.2, AC-11 « Limite »)* ;
à chaque écriture, c'est le **message du §14.2.2**.
⚠️ **Et ce n'est PAS observé** — borne **NM-10**, §14.8.

   **vrai quoi qu'il arrive**)*. **La surface existe** au §14.1.2 ; ⛔ **le refus ne sera pas
   démontré** sur cet hôte, et ⛔ **il ne doit pas être déguisé en scénario vert**.
4. 🔴 **Le comportement web d'AC-17 est une PRESCRIPTION, jamais une observation** *(borne **NM-10** :

   PAS avec US-01.3**, qui vise iOS/Android — contrairement à NM-1, NM-2, NM-4, NM-6, NM-7.
5. **Rien ici ne LÈVE un AC.** Un design ne couvre pas une clause : il la rend **observable**. **AC-16
